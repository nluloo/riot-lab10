## 1. Архитектура и компоненты в Kubernetes

Серверное приложение аренды автомобилей упаковано в контейнер на базе .NET 8 и управляется оркестратором Kubernetes:

```
[Клиент C# / test_client.py]
          │
          │ TCP: localhost:5000 (через kubectl port-forward)
          ▼
┌────────────────────────────────── Kubernetes Cluster (k3s) ──────────────────────────────────┐
│                                                                                              │
│   Service: riot-server (ClusterIP, port: 5000 -> targetPort: 5000, selector: app=riot-server)│
│                                      │                                                       │
│                   ┌──────────────────┴──────────────────┐                                    │
│                   ▼                                     ▼                                    │
│   Pod: riot-server-xxx (Replica 1)      Pod: riot-server-yyy (Replica N)                     │
│   - Image: riot-server:1.0              - Image: riot-server:1.0                             │
│   - Env: APP_MODE from ConfigMap        - Env: APP_MODE from ConfigMap                       │
│   - Ports: 5000                         - Ports: 5000                                        │
│                   │                                     │                                    │
│                   ├──────────────────┬──────────────────┤                                    │
│                   ▼                  ▼                  ▼                                    │
│          Service/Pod: broker   Service/Pods: node1..node5   Service/Pod: primary & replica   │
│          (Pub/Sub, port 5001)  (Consensus, ports 6001..6005) (PostgreSQL 16, port 5432)     │
│                                                                                              │
│   ConfigMap: riot-config (APP_MODE: "kubernetes")                                            │
└──────────────────────────────────────────────────────────────────────────────────────────────┘
```

### Основные манифесты
* [`configmap.yaml`](configmap.yaml): хранит неконфиденциальный параметр `APP_MODE: "kubernetes"`.
* [`deployment.yaml`](deployment.yaml): задает желаемое состояние приложения (`replicas: 3`, образ `riot-server:1.0`, селекторы `app: riot-server`, проброс `APP_MODE` через `configMapKeyRef`, переменные подключения к `primary`, `broker` и 5 узлам кластера).
* [`service.yaml`](service.yaml): предоставляет единую стабильную точку входа `ClusterIP` на порт 5000, балансирующую трафик между подами серверного приложения.
* [`broker.yaml`](broker.yaml): Deployment и Service брокера сообщений Pub/Sub (`riot-broker:1.0`, порт 5001).
* [`cluster-nodes.yaml`](cluster-nodes.yaml): Deployments и Services для 5 узлов распределенного консенсуса (`riot-nodes:1.0`, порты 6001–6005).
* [`postgres.yaml`](postgres.yaml): база данных PostgreSQL для обеспечения полного цикла предметных операций.

## 4. Результаты выполнения Части 3: Масштабирование и отказ Pod

### Шаги эксперимента
1. Масштабирование вверх до 3 экземпляров:
   `kubectl scale deployment riot-server --replicas=3`
   *Все 3 Pod перешли в состояние Running (`riot-server-78b67c8d74-596m5`, `riot-server-78b67c8d74-tb4vp`, `riot-server-78b67c8d74-vf8b4`).*
2. Масштабирование вниз до 2 экземпляров:
   `kubectl scale deployment riot-server --replicas=2`
   *Один Pod был плавно остановлен сигналом SIGTERM, осталось ровно 2 активных Pod.*
3. Повторное масштабирование вверх до 3:
   `kubectl scale deployment riot-server --replicas=3`
   *Поднят новый Pod, общее число экземпляров — 3.*
4. Моделирование отказа Pod:
   `kubectl delete pod riot-server-78b67c8d74-4xhbc`
   *Удаленный Pod завершен, контроллер Deployment ReplicaSet мгновенно зарегистрировал расхождение желаемого (3) и фактического (2) состояния и создал новый Pod `riot-server-78b67c8d74-xntn8`.*
5. Проверка доступности через Service:
   *Клиентские операции продолжают успешно выполняться без сбоев соединения.*

### Анализ вопросов Части 3:
* **Почему Kubernetes создал замену удаленному Pod?**  
  Deployment управляет объектом ReplicaSet, непрерывный цикл согласования (*reconciliation loop*) которого сопоставляет фактическое количество запущенных Pod с полем `spec.replicas`. При обнаружении нехватки подов создаётся новый.
* **Как Deployment определяет желаемое количество экземпляров?**  
  Из декларативного описания в поле `spec.replicas` манифеста или текущего состояния объекта в etcd/k3s SQLite.
* **Почему количество Pod может временно отличаться от заданного?**  
  Требуется время на планирование (*Scheduling*), выделение IP, вытягивание образов и запуск контейнеров (*ContainerCreating*).
* **Почему наличие трех Pod не гарантирует сохранность данных при отказе базы данных?**  
  Поды сервера являются stateless-компонентами (вычисления и протокол), а транзакционные данные хранятся во внешней/отдельной базе данных. Падение СУБД делает невозможным выполнение операций всеми подами.
* **Почему масштабирование не всегда приводит к ускорению приложения?**  
  Узким местом часто становится общая база данных (блокировки строк/транзакций), сетевая пропускная способность либо конкуренция за общий ресурс (свободный автомобиль).

## 6. Сравнение Docker / Docker Compose и Kubernetes

| Критерий | Docker / Docker Compose | Kubernetes |
|---|---|---|
| **Основная задача** | Запуск контейнеров на одном хосте, локальная разработка | Оркестрация распределённых контейнеров на кластере узлов |
| **Описание конфигурации** | `Dockerfile` и `compose.yaml` | Декларативные манифесты YAML (`Deployment`, `Service`, `ConfigMap`) |
| **Запуск приложения** | `docker compose up` | `kubectl apply -f` с диспетчеризацией через kube-scheduler |
| **Управление экземплярами** | Перезапуск локального контейнера при падении процесса | Автоматический контроль желаемого состояния через ReplicaSet |
| **Организация доступа** | Проброс портов на хост, внутренняя сеть Docker DNS | Ресурс `Service` (ClusterIP/NodePort) со стабильным IP и DNS |
| **Изменение числа экземпляров** | Ручное изменение флагом `--scale` на одном хосте | `kubectl scale` или автоматическое масштабирование (HPA) |
| **Реакция на удаление экземпляра** | Контейнер останавливается, замена не создаётся | Контроллер немедленно поднимает новый Pod взамен удалённого |
| **Диагностика ошибок** | `docker logs`, `docker inspect` | `kubectl logs`, `kubectl describe pod` (лента событий Events) |
| **Требования к среде** | Достаточно одного компьютера с Docker Engine | Кластер Kubernetes (Control Plane, Worker Nodes, CNI, CRI) |

## 7. Ответы на контрольные вопросы методички

1. **Что такое Kubernetes и для чего он используется?**  
   Kubernetes — это открытая платформа оркестрации контейнеризированных приложений, предназначенная для автоматизации их развертывания, масштабирования, балансировки нагрузки и обеспечения отказоустойчивости в кластере.
2. **Чем Kubernetes отличается от Docker?**  
   Docker — это инструмент сборки образов и среда выполнения отдельных контейнеров на одном хосте. Kubernetes управляет жизненным циклом множества контейнеров, распределенных по кластеру из многих физических или виртуальных машин.
3. **Что такое Kubernetes Cluster?**  
   Совокупность управляющих узлов (Control Plane: API Server, etcd, Scheduler, Controller Manager) и рабочих узлов (Worker Nodes с kubelet и kube-proxy), на которых запускаются контейнеризированные рабочие нагрузки.
4. **Что такое Pod?**  
   Минимальная единица развертывания в Kubernetes, представляющая собой группу из одного или нескольких тесно связанных контейнеров с общими сетевыми пространствами имен (IP-адресом), томами и IPC.
5. **Чем Pod отличается от Docker Container?**  
   Контейнер Docker — это единичный изолированный процесс операционной системы. Pod — это абстракция Kubernetes, которая может объединять несколько взаимосвязанных контейнеров с общим жизненным циклом, IP-адресом и файловыми хранилищами.
6. **Что такое Deployment?**  
   Декларативный контроллер более высокого уровня, который управляет ReplicaSet, обеспечивая развертывание, обновление (rolling update), откат и поддержание заданного количества реплик Pod.
7. **Для чего используется параметр replicas?**  
   Задает желаемое постоянное количество одновременно работающих идентичных экземпляров (Pod) в рамках развертывания.
8. **Что такое Service?**  
   Абстракция Kubernetes, определяющая логический набор Pod и стабильную сетевую политику доступа к ним (виртуальный IP-адрес ClusterIP, DNS-имя, балансировка трафика).
9. **Почему клиенту неудобно обращаться к Pod напрямую?**  
   Поды являются эфемерными: при падении, перезапуске или масштабировании Pod удаляется, а вновь созданный получает новый динамический IP-адрес. Прямое обращение привело бы к частым обрывам и необходимости постоянного отслеживания адресов клиентом.
10. **Для чего используются метки (Labels) и селекторы (Selectors)?**  
    Метки — пары «ключ-значение», прикрепляемые к объектам для их категоризации. Селекторы используются сервисами и контроллерами (Deployment, ReplicaSet) для гибкой выборки и маршрутизации запросов к нужным объектам.
11. **Что такое YAML и для чего он используется в Kubernetes?**  
    YAML — человекочитаемый формат сериализации данных. В Kubernetes YAML служит стандартом для декларативного описания желаемого состояния всех ресурсов кластера.
12. **Как проверить состояние Pod?**  
    Командой `kubectl get pods`, которая отображает имя, статус (`Running`, `Pending`, `CrashLoopBackOff`), количество готовых контейнеров и время работы.
13. **Как получить подробную информацию о Pod?**  
    Командой `kubectl describe pod <имя-pod>`, которая выводит детальное описание конфигурации, IP-адреса, смонтированные тома, переменные окружения и chronological-список событий (`Events`).
14. **Что происходит при удалении Pod, управляемого Deployment?**  
    Контроллер ReplicaSet регистрирует расхождение текущего числа активных подов с желаемым (`replicas`), и мгновенно создает новый Pod взамен удаленного.
15. **Почему восстановление Pod не гарантирует сохранность данных?**  
    Внутренняя файловая система Pod не сохраняется при его удалении. Если данные не были записаны во внешнюю постоянную БД или постоянный том (`PersistentVolume`), они будут безвозвратно утеряны.
16. **Что такое ConfigMap?**  
    Ресурс Kubernetes для хранения неконфиденциальных параметров конфигурации в виде пар ключ-значение, передаваемых в контейнеры через переменные окружения, аргументы командной строки или файлы конфигурации.
17. **Для чего используются переменные окружения?**  
    Для динамической передачи параметров выполнения в процесс приложения без необходимости перекомпиляции исходного кода или пересборки Docker-образа.
18. **Для чего используется kubectl port-forward?**  
    Для создания временного защищенного TCP-тоннеля между локальным портом компьютера разработчика и портом пода/сервиса внутри кластера Kubernetes.
19. **Почему несколько Pod на одном компьютере не обеспечивают защиту от отказа этого компьютера?**  
    Все эти поды разделяют аппаратные ресурсы (процессор, оперативную память, питание, сеть) одного физического узла. Выход узла из строя приведет к одновременной недоступности всех размещенных на нем подов.
20. **Чем Docker Compose отличается от Kubernetes?**  
    Docker Compose предназначен для локального описания и запуска многоконтейнерных приложений на одной машине. Kubernetes — это промышленный распределенный оркестратор для кластеров из десятков и сотен серверов с функциями самовосстановления, сетевой маршрутизации, масштабирования и управления конфигурациями.
