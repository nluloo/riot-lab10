Предметная область: «Аренда автомобилей» (вариант 11, C#/.NET 8, Jenkins, Git, Docker, Kubernetes k3s)

1. Архитектура и структура CI/CD Pipeline

В рамках ЛР №10 ручной процесс сборки, тестирования и раскатки распределенного приложения аренды автомобилей заменен полностью автоматизированным конвейером Jenkins Pipeline на основе практики «Pipeline as Code» (Jenkinsfile). Конвейер интегрирует распределенный стек: исходный код в Git, компиляцию и прогон 129 тестов через .NET SDK 8.0, контейнеризацию в Docker и доставку в промышленный кластер Kubernetes (k3s).

Конвейер включает 6 строго последовательных этапов:

  1. Checkout: Извлечение коммита из ветки main Git-репозитория.
  2. Restore: Восстановление внешних NuGet-зависимостей (dotnet restore).
  3. Build: Компиляция решения в конфигурации Release без повторного восстановления (dotnet build --no-restore).
  4. Test: Запуск полного набора из 129 Unit-, интеграционных и нагрузочных тестов с генерацией отчета в формате Visual Studio .trx. При падении хотя бы одного теста конвейер немедленно прерывается.
  5. Package: Сборка многоэтапного Docker-образа riot-server:%BUILD_NUMBER%.
  6. Deploy: Доставка образа в хранилище containerd узла k3s (через sudo k3s ctr images import), обновление образа подов развертывания через kubectl set image и контроль плавного обновления (Rolling Update) командой kubectl rollout status.

Структура проекта: манифесты Kubernetes вынесены в каталог k8s-manifests/ (deployment.yaml, service.yaml, configmap.yaml, broker.yaml, cluster-nodes.yaml, postgres.yaml); конфигурация доступа kubeconfig изолирована в k3s-config/k3s.yaml; автоматизация выкатки оформлена в deploy_to_k3s.py.

2. Результаты выполнения этапов и моделирования сбоев

1. Настройка окружения и Jenkins: Сервер Jenkins запущен на порту 8085 с выделенным JENKINS_HOME. Для безопасного чекаута из локального Git-репозитория активирован флаг -Dhudson.plugins.git.GitSCM.ALLOW_LOCAL_CHECKOUT=true. Создано задание Pipeline RIOT-CICD.

2. Прогон тестов и генерация отчетов: В Сборке #3 успешно выполнены этапы сборки и тестирования решения. Все 129 тестов (покрывающие базу данных, репликацию, консенсус узлов, брокер Pub/Sub и валидацию манифестов k8s) завершились со статусом Passed за 1 минуту 20 секунд, сформирован отчет результатов .trx.

3. Моделирование ошибки тестирования (Сборка #4): В тест KubernetesConfigTests.cs внесена искусственная ошибка утверждения. Команда dotnet test завершилась с ошибкой (exit code 1). Jenkins зафиксировал сбой этапа Test и прервал пайплайн. Этапы Package и Deploy были пропущены. Непротестированный код не попал в Docker и не был раскатан в кластер.

4. Автоматическое развертывание в k3s (Сборка #5): После исправления теста пайплайн выполнил все 6 этапов: собран образ riot-server:5, передан на узел кластера и развернут на 3 репликах без простоя сервиса.

5. Моделирование ошибки развертывания (Сборка #6): Для проверки защитных механизмов оркестратора в манифесте развертывания временно указан несуществующий образ riot-server:broken-tag-err с таймаутом раскатки 15 секунд:

  • Jenkins зафиксировал сбой на этапе Deploy по истечении таймаута команды kubectl rollout status (exit code 1).
  • В Kubernetes новый Pod перешел в статус ErrImagePull и ImagePullBackOff.
  • Критически важный результат: Оркестратор сохранил в работе все 3 старых пода, трафик пользователей не прерывался (*Zero Downtime*).

6. Автоматическое обновление приложения (Сборка #7): В исходный код сервера внесены изменения версии (суффикс [v2.0-cicd]). Изменения зафиксированы в Git и отправлены на сборку. Jenkins автоматически пересобрал решение, запустил тесты, упаковал образ riot-server:7 и успешно обновил Deployment в кластере k3s.

7. Проверка доступности через Service: Через локальный порт-форвард сервиса svc/riot-server:5000 выполнены 3 предметные операции:

  • SearchCar — найдено 3 автомобиля, подтверждена работа обновленной версии [v2.0-cicd].
  • CreateRental — аренда #3 успешно зафиксирована в Primary, согласована кворумом узлов (5 из 5 голосов, кворум 3) и опубликована брокеру сообщений Pub/Sub.
  • ReturnCar — автомобиль возвращен, состояние БД синхронизировано (версия данных LSN = 6).

Ответы на контрольные вопросы методички

1. Что такое Continuous Integration? Continuous Integration (непрерывная интеграция, CI) — практика разработки программного обеспечения, при которой разработчики регулярно объединяют изменения исходного кода в общей ветке Git-репозитория, после чего каждое изменение автоматически собирается и тестируется с целью скорейшего выявления интеграционных ошибок и конфликтов. В работе это реализовано этапами Checkout, Restore, Build и Test (запуск 129 тестов в Сборке #3).
2. Что такое Continuous Delivery? Continuous Delivery (непрерывная доставка, CD) — методология поставки ПО, расширяющая CI, при которой каждое прошедшее автоматические проверки изменение автоматически собирается в готовый к релизу артефакт (например, Docker-образ или архив) и может быть развернуто в тестовое или промышленное окружение нажатием одной кнопки (с ручным подтверждением).
3. Чем Continuous Delivery отличается от Continuous Deployment? При Continuous Delivery шаг развертывания в продуктивную среду требует ручного подтверждения (ручной approval gate), в то время как при Continuous Deployment развертывание в production полностью автоматизировано и происходит без участия человека для каждого коммита, успешно прошедшего тестирование. Наш конвейер в Jenkins реализует Continuous Deployment: шаг Deploy в k3s запускается автоматически вслед за шагом Package.
4. Что такое Pipeline? Pipeline (конвейер) — автоматизированная последовательность стадий (stages) и шагов (steps), описывающая весь процесс жизненного цикла поставки приложения от получения исходного кода до сборки, тестирования и развертывания. В работе конвейер описан декларативно в файле Jenkinsfile.
5. Для чего используется Jenkins? Jenkins — ведущий сервер автоматизации с открытым исходным кодом, предназначенный для оркестрации процессов CI/CD, выполнения сборочных конвейеров, управления распределенными агентами, интеграции с Git, Docker, Kubernetes и публикации отчетов о тестировании. В работе запущен на порту 8085 и управляет заданием RIOT-CICD.
6. Что такое Jenkins Job? Jenkins Job (задание) — отдельная сконфигурированная сущность в Jenkins, определяющая параметры, триггеры запуска, шаги выполнения задач и правила архивации результатов для конкретного проекта или компонента.
7. Чем Jenkins Pipeline отличается от обычного Jenkins Job? Обычный (Freestyle) Job настраивается вручную через формы веб-интерфейса, имеет линейную структуру и не версионируется вместе с кодом. Jenkins Pipeline строится по принципу «Pipeline as Code», описывается в файле Jenkinsfile на базе синтаксиса Groovy DSL, хранится в репозитории Git, поддерживает визуализацию стадий, условия выполнения и параллельные ветки.
8. Что такое Jenkinsfile? Jenkinsfile — текстовый файл конфигурации, хранящийся в корневом каталоге Git-репозитория и содержащий декларативное или скриптовое описание этапов, шагов, параметров окружения и агентов выполнения CI/CD конвейера. В нашей работе содержит секции pipeline { agent any stages { ... } }.
9. Для чего используется этап Restore? Этап Restore выполняет команду dotnet restore, которая скачивает все объявленные в файлах *.csproj внешние зависимости и пакеты NuGet (например, Npgsql, xUnit), сверяет их версии и подготавливает локальный кэш проекта к компиляции, гарантируя идентичность окружения.
10. Почему тесты необходимо запускать до создания Docker-образа? Запуск тестов до этапа сборки контейнера позволяет предотвратить трату времени процессора, места на диске и сетевого трафика на упаковку заведомо неработоспособного кода. Это исключает попадание дефектных версий в реестр контейнеров и их случайное развертывание в кластере.
11. Что происходит, если тесты завершаются ошибкой? Утилита dotnet test возвращает ненулевой код возврата (exit code 1). Jenkins регистрирует сбой на этапе Test, отмечает всю сборку красным статусом FAILURE и немедленно прекращает выполнение конвейера. Этапы Package и Deploy блокируются и пропускаются (продемонстрировано в Сборке #4).
12. Что выполняется на этапе Package? На этапе Package выполняется создание исполняемого артефакта поставки — Docker-образа приложения (команда docker build -t riot-server:%BUILD_NUMBER% .), в который инкапсулируются бинарные сборки сервера, среда выполнения .NET 8 Runtime и системные зависимости.
13. Для чего используется этап Deploy? Этап Deploy автоматизирует выкатку собранного контейнера в среду исполнения: передает образ на узлы кластера Kubernetes, обновляет манифест Deployment (команда kubectl set image) и контролирует успешный перевод подов на новую версию без простоя пользователей.
14. Как Jenkins может обновить Docker-образ в Kubernetes Deployment? С помощью запуска команды kubectl set image deployment/riot-server server=riot-server:<тег> через утилиту kubectl, настроенную на авторизацию в API-сервере через файл kubeconfig или токен служебной учетной записи (ServiceAccount).
15. Для чего используется команда kubectl rollout status? Команда kubectl rollout status deployment/<имя> блокирует выполнение до тех пор, пока оркестратор не завершит раскатку: убедится, что все новые поды запустились и прошли проверки готовности (Ready), а старые поды корректно остановлены. Если развертывание зависает или завершается ошибкой (например, ImagePullBackOff), команда завершается с ненулевым кодом по таймауту, позволяя Jenkins зафиксировать сбой.
16. Почему Jenkins должен иметь доступ к Kubernetes? Потому что процесс Jenkins выступает драйвером доставки (CD): без доступа к API-серверу Kubernetes Jenkins не может инициировать обновление конфигурации, проверять статус подов и управлять жизненным циклом рабочих нагрузок в кластере.
17. Что такое Poll SCM? Poll SCM — механизм автоматического триггера в Jenkins, который по периодическому расписанию (cron-выражению) опрашивает удаленный Git-репозиторий на наличие новых коммитов в отслеживаемой ветке. При обнаружении новых изменений Jenkins автоматически запускает конвейер без необходимости настройки внешних Webhook.
18. Что может привести к неуспешному выполнению Jenkins Pipeline? К неуспешному выполнению конвейера могут привести: ошибки доступа к репозиторию или конфликты слияния на шаге Checkout; отсутствие пакетов в NuGet или сетевые сбои на шаге Restore; синтаксические и типовые ошибки кода на шаге Build; провал assertion в юнит- или интеграционных тестах на шаге Test; ошибки синтаксиса Dockerfile или нехватка места на шаге Package; недоступность API Kubernetes, неверный тег образа (ImagePullBackOff) или зависание контейнера (CrashLoopBackOff) на шаге Deploy.
